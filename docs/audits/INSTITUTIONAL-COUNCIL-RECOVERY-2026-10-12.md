## Confirmed recovery bug on current release

`backend/bookingrecovery.js` queried only `.limit(100)` for each of `awaiting_payment`, `awaiting_assignment` and `refundPending && status=cancelled`, without cursor or progress marker. If the first 100 records were recent, unexpired, or permanently failed refunds, the same records were read every minute and newer/older outstanding records beyond the first page were never examined. This is unacceptable for timely paid cancellation/refund recovery, and needlessly repeats Firestore document reads. Existing test already covered 125 **irrelevant** flags excluded by filtering, but not 251 **qualifying** first-page records.

## Proposed minimal remedy and limitations

Use Firestore indexed document-name ordering and `startAfter(lastId)` with three stable checkpoint fields in a single `recovery_cursors/booking_recovery` document. Read that one checkpoint once per leased sweep; read at most 100 records per group; advance to last attempted record on a full page; wrap to the beginning once at the end. Commit checkpoint **after processing** so crashes cannot silently lose obligations and pre-existing Stripe idempotency protects repeats. A checkpoint read/write failure must be reported, never misrepresented as healthy. Writes occur only when an active cursor changes. This adds one checkpoint document read per sweep and occasional small write, but avoids unbounded offset reads. Exact Firestore billing, index availability and convergence speed at one million real obligations remain unmeasured. Saturation must be visible and cause capacity investigation, not automatic unpriced server upgrades.

**Acceptance:** existing 4-case canonical recovery suite plus twice-run 251-record starvation, persistence across fresh sweeps, bounded reads, end-of-range wrap, failed checkpoint read/write and unchanged cancellation/refund idempotency. All protected exact-head GitHub workflows and emulator security tests must pass before merging. Firestore SDK/index behavior requires a live controlled follow-up; an isolated fake alone cannot prove deployed index availability.

## Business-design Council verdict (research synthesis, not endorsements)

Ford's process viewpoint favors few repeatable low-cost automated flows; Rockefeller's capital viewpoint favors measured contribution per Travel rather than vanity registrations; Jobs/Apple's product viewpoint favors one clear Traveler total, accessible simple responses, and phone-first founder control. Apply MIT/HBS/Stanford's matching economics and IDEO/NNG's user tests **without pretending those people/institutions personally reviewed or endorsed this code**.

**No launch authorization:** No new jurisdiction, insurer purchase, real rides, refunds, payouts or fare changes are performed by this evidence or PR. Existing legal, financial, physical-device, provider and real-scale launch gates stay open.
