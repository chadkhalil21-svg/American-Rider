## Specific source-to-code finding and correction

`backend/monitor.js` uses `Promise.allSettled()` to attempt emergency notification to BOTH Traveler and Operator independently. The pre-existing expression `r.status === 'fulfilled' && r.value?.ok !== false` misclassified a fulfilled promise with `undefined`, `null`, `{}` or other undefined success shape as having notified a person. This is a false-success claim in a safety-critical return report.

**Change:** count notification acceptance only for `r.status === 'fulfilled' && r.value?.ok === true`. Adversarial `backend/monitor.test.js` scenarios now inject absent, null, malformed and numeric-false results and require: emergency stored, case still raised, other person's push still attempted, `report.ok=false`, explicit delivery failure. This change makes the report *less optimistic*; it does **not** make Expo tickets proof of on-device delivery.

**Separate open safety gap:** `backend/push.js` returns Expo ticket IDs but has no evidenced durable provider **receipt** retrieval/acknowledged handset path. A received push ticket must not be equated with observed iOS/Android receipt, foreground display, emergency-screen navigation, or a staffed human response. Record tests by device/build/OS, ticket ID, receipt ID/status, actual handset observation, app state and case acknowledgment. A crash, revoked permission, stale token, OS battery optimization and background force-quit must not be hidden.

\n### Token-rotation race closed\n\nWhile an Expo send was outstanding, the user could register a replacement push token. Previously a late `DeviceNotRegistered` on the **old** token unconditionally set the user's stored pushToken to null, erasing the new registration. `backend/push.js` now only clears the *rejected token* inside an atomic Firestore transaction if the current stored token still matches. `backend/push-acceptance.test.js` simulates rotation during the network call and normal invalid-token clearing. This addresses server-side token loss; Expo receipts and physical-device display remain unverified.\n
## Database performance and economic exposure

`backend/monitor.js` pages **all** currently active accepted/arrived/onboard Travels in blocks of 200 on every 60-second monitor sweep. It does not restrict monitoring to only newly changed records. At **1,201 continuously active Travels**, a steady full scan would return at least **1,729,440** document reads in one day (1,201 x 1,440); add index-entry reads, other periodic sweeps, snapshots, dispatch, writes and client listeners. This is *workload extrapolation*, not an actual Firestore bill.

Added `infra/rules-emulator/monitor-load.test.cjs` to the release gate. It writes **1,201 synthetic active** and 13 cancelled documents to the **real local Firestore emulator**, executes TWO complete paginated query scans and checks all 1,201 newly seeded active records are reached without duplication, excludes cancelled records, and counts all pages; earlier authentication/rules tests also leave a few valid active Travel fixtures in the same emulator, which a genuine all-active scan must count too. The first CI run caught this test-isolation assumption (1,205 total active records versus 1,201 new seed records) and the assertion was corrected rather than deleting other valid records. It reports actual emulator elapsed time and visible document/page counts. The test does NOT load production, touch customer data, establish Firestore cloud billed reads or index reads, certify p95/p99 response times, validate high-concurrency writes or prove 1M live-booking throughput.

**Render baseline inspection, 11–12 October UTC:** single server instance; sampled CPU use very low (peak around 0.006 cores); reported memory max ~139 MB; a small number of HTTP requests; no usable p95 latency series. These low-load observations cannot determine peak requests per second, a live Firestore budget or an upgrade threshold. The production backend remained on revision `b543c9b1` at inspection while `release/current` had merged documentation PR #153; a new deployment must be separately checked after any production code merge.
